# 用户聊天与个人信息安全方案（领导汇报版）

## 一、汇报结论

当前系统需要在服务器完成 VAD、ASR、LLM、TTS 和长期记忆处理，因此服务端运行时会接触聊天明文。仅靠后台权限或数据库加密，不能保证拥有应用调试权限的 root 运维人员绝对看不到明文。

行业成熟方案分为三个等级：

1. **企业级数据保护**：权限分离、应用层加密、客户密钥、审计，可防后台人员和数据库管理员直接查看。
2. **机密计算**：在受保护内存中解密和处理，通过远程证明向可信程序发放密钥，可降低宿主机 root 和容器调试风险。
3. **端到端加密**：服务器只转发密文，可实现平台不掌握聊天正文，但需要改变当前 ASR/LLM/TTS 架构。

**建议：先建设企业级方案，同时预留机密计算升级路径；如果要求平台本身完全不可见，再评估端到端加密。**

## 二、需要保护的数据

| 类别 | 内容 |
| --- | --- |
| 聊天内容 | 语音转文字、用户提问、模型回复、聊天摘要 |
| 音频内容 | 用户语音、机器人语音、声纹样本 |
| 个人信息 | 手机号、姓名、设备、声纹、人脸、地址 |
| 运行元数据 | IP、设备 ID、时间、会话和关系信息 |

## 三、公开产品案例

| 架构 | 已使用的软件/平台 | 能力与边界 |
| --- | --- | --- |
| 端到端加密 | Signal、WhatsApp、Matrix/Element | 服务器通常不能读取正文；搜索、统一审计和服务端摘要受限 |
| 客户密钥/信封加密 | Microsoft 365、Google Workspace、Slack Enterprise | 数据库和备份无客户密钥不能解密；应用运行时仍可能处理明文 |
| 客户端加密存储 | Proton Mail、Proton Drive | 服务端保存密文，客户端解密；多端同步和搜索更复杂 |
| 可选端到端加密 | Zoom E2EE | 参与方解密；云端录制和部分功能受限 |
| 机密计算 | AWS Nitro Enclaves、Azure Confidential、Google Confidential Space | 保护受保护内存；需要专用硬件/云平台和系统改造 |

微信、QQ、飞书公开资料主要体现传输加密、存储保护、租户隔离、审计和合规能力；公开资料不足以证明普通聊天默认采用 Signal 式“服务器无法解密”。

## 四、三种方案对比

| 方案 | 防后台人员 | 防数据库管理员 | 防服务器 root | 当前适配度 |
| --- | ---: | ---: | ---: | ---: |
| 权限控制 | 是 | 否 | 否 | 立即适用 |
| 应用层加密 + 独立 KMS | 是 | 是 | 部分 | 推荐第一阶段 |
| 机密计算 + 远程证明 | 是 | 是 | 较强 | 第二阶段评估 |
| 端到端加密 | 是 | 是 | 是 | 需要重构 |

## 五、推荐目标架构

### 第一阶段：企业级数据保护

```text
ESP32/用户设备 --TLS--> xiaozhi-server/manager-api
                               |
                 应用层信封加密、密钥由独立 KMS/Vault 管理
                               |
                    MySQL/Redis/对象存储只保存密文
```

必须同步实施：运维、数据库、应用发布、密钥和审计分权；运维默认没有聊天查看、音频播放、记忆查看和导出权限；下载/播放使用短时效票据；所有解密和导出操作审计；生产关闭远程调试并禁止 Docker socket；备份加密。

目标：**运维人员不能通过后台、数据库、备份和普通文件直接看到聊天内容。**

### 第二阶段：机密计算

将聊天解密、ASR、LLM、TTS 和记忆处理放入 TEE/机密工作负载，KMS 仅向通过远程证明的可信程序发放密钥。

目标：**降低宿主机 root、Docker 管理员和容器调试读取运行时明文的风险。**

### 第三阶段：端到端加密

由客户端或可信边缘设备完成加密、解密和模型处理，服务器只保存和转发密文。

目标：**服务器平台本身不掌握聊天正文。**代价是需要重新设计服务端 ASR/LLM/TTS、搜索、摘要、长期记忆和多端同步。

## 六、项目实施计划

### 0—1 个月：风险收口

- 完成聊天、音频、记忆、导出和播放接口清单；
- 关闭匿名聊天下载和播放，修复跨工作空间/智能体/会话访问；
- 运维角色默认禁止内容访问；
- 日志不得输出聊天正文、音频、Token 和个人敏感信息。

### 1—3 个月：企业级加密

- 建立 KMS/Vault 或客户自持密钥方案；
- 加密聊天正文、音频、指标、记忆和个人信息；
- 完成历史数据和备份加密迁移；
- 建立解密、导出、播放和管理员操作审计。

### 3—6 个月：机密计算评估

- 选择支持 TEE 的云平台或硬件；
- 验证实时 ASR/LLM/TTS 性能；
- 实现远程证明和 KMS 按证明发钥匙；
- 进行 root、Docker 调试和内存读取对抗测试。

## 七、需要领导确认

1. 目标是“运维人员不能直接查看”，还是“宿主机 root 也不能获取运行时明文”？
2. 是否接受端到端加密导致服务端搜索、摘要、长期记忆和统一审计受限？
3. 是否允许采购独立 KMS/Vault，并将服务器运维、数据库、应用发布和密钥管理分权？

## 八、最终建议

```text
接口和权限收口
  -> 运维/数据库/KMS 分权
  -> 应用层信封加密
  -> 机密计算保护运行时明文
  -> 必要时再做端到端加密
```
