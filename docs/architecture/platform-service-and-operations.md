# 平台服务额度与运营隔离

本文描述产品化实现的身份、凭据和额度边界。供应商账单的数据来源、证据规则和资源包查询继续以[模型管理](../models/model-management.md#11-模型用量与实际消费管理)为准；生产升级统一遵循[生产部署入口](../deployment/private-docker-release.md)。

## 1. 用户端与运营端

Web 构建包含用户入口 `index.html` 和员工入口 `ops.html`，员工使用独立的账号、TOTP、会话和导航。移动端只承担用户业务。两套页面仍由现有服务发布，前端隐藏菜单不是权限依据：Java 同时校验会话 audience、岗位权限和资源所有权。

不再保留超级管理员角色或租户内容旁路。员工主体没有租户 `userId`，不能凭运营身份访问用户聊天、音频、私人记忆或知识库，也不能通过后台重置用户密码获得其登录身份。

岗位模板由代码限定，员工不能编辑权限字符串或委派上限。额度、供应商财务、凭据、模型目录、官方内容、OTA、运维、支持、身份申请/审批和审计分别授权。发布与审核、申请与批准之间继续检查职责冲突，不以把多个岗位相加的方式恢复全权账号。

这些是应用权限边界。持有宿主 root、数据库明文访问或任意部署代码权限的人员仍可能越过应用；生产需要独立的部署身份、密钥管理、数据库权限及基础设施审计，不能把页面隔离宣传为对 root 的隐私保护。

## 2. 固定负责人与个人凭据

| 场景 | 供应商凭据所有者 | 平台额度承担者 |
| --- | --- | --- |
| 本人拥有的工作空间 | 本人 | 本人 |
| 受邀在他人工作空间协作或设备调用 | 该工作空间的固定负责人 | 同一负责人 |

项目只有一种工作空间：每位用户默认拥有自己的空间，可以邀请其他用户协作，默认标记不限制协作。所有调用都使用所在空间固定负责人的凭据与额度。当前不提供负责人交接；负责人不能直接退出、被移除或降级，不可在负责人不可用时改扣成员账户。

注册创建独立额度账户并尝试从库存分配凭据。库存不足显示待开通，不能回退到共享模型密钥。旧用户的额度不会由迁移自动发放，旧全局密钥也不会自动分配给某个用户。

凭据按用户托管和加密，浏览器、移动端和设备只能读掩码及状态。DeepSeek 与火山分别配置；火山方舟 LLM 和豆包语音使用对应服务凭据，不将一份 API Key 当作跨产品通用密钥。相同上游秘密不得重复分配给不同用户，已分配凭据不回收给他人，轮换保留历史归属。

工作空间限额是负责人账户内的消费约束，不产生独立余额。其他成员只能查看获准的空间用量、限额和服务状态，不得读取负责人完整个人余额。

## 3. 两套账与调用准入

平台额度与供应商实际费用是独立台账。服务额度由平台运维按岗位权限统一下发，平台消费按内部费率规则结算。当前 Web 与移动端的用户页面只展示额度、用量、流水和服务状态，不提供额度申请、申请记录、充值、支付、提现或转账入口；额度不足时提示联系平台运维处理。供应商实际费用必须有官方金额证据，不能把平台扣减额或预占额标成实际云成本。

已有额度申请表、接口和后台处理能力保留内部兼容与历史追溯，不属于当前发布的用户体验；运维可直接通过授权发放功能下发额度，无需用户先申请。注册试用政策是默认关闭的内部能力，启用必须经过运维确认，不能据此承诺注册即获额度。后续商业化可以保留架构设计，本阶段不新增支付实现、接口或用户界面。上述界面调整不改变后台权限、幂等账本和既有历史记录。

未来支付扩展应位于独立的订单与支付渠道层：只有经过验签、金额核对和幂等处理的入账事件，才能进入既有额度发放服务；订单资金流水、平台服务额度和供应商成本继续分别核算。当前仅记录这一扩展边界，不创建支付路由、订单表或前端占位入口。

运维统一下发也包括经授权启用的自动发放政策。已生效的试用或其他政策发放仍按账本事实展示在用户额度流水中，用户不能自行领取或启用政策；移除申请与支付界面不隐藏历史发放来源。

每次调用由服务端解析工作空间、智能体、设备、实际发起者、固定负责人、凭据版本和费率版本，冻结到执行许可。客户端不得自报付款人。

调用顺序为：校验资源和账户 → 锁定可用额度 → 预占有界用量 → 持久保存调用标识 → 确认开始 → 使用许可内凭据访问批准的供应商 → 按可信用量幂等结算。Python `/config/platform/**` 使用内部服务身份与已签发的上下文；Java 执行器沿用同一准入服务。

`admit` 按 attempt 幂等，`start` 防止重复派发，`extend` 必须先增加预占才能发送下一段付费数据，`settle` 保留原归属，`release` 仅释放确定尚未执行的调用。短期许可有硬截止时间；新调用和续占重新检查当前授权、账户和凭据状态。

Token、音频毫秒、计费字符是内部费率的基础单位。预占所用上界不是供应商实际用量；最终实际用量只取供应商已确认字段。结果未知或用量不完整时保留待核对预占，不虚构零消费。结算与供应商账单是否已关联是两个独立状态。

Python SQLite 补传队列保存调用及结算能力引用，不保存模型 API Key、提示词或音频。Java 同样保留结算补传。只有相关台账接受后才删除本地回执；异常记录保留并轮转重试，避免阻塞其他用户账目。队列必须持久挂载和备份，不得当作缓存清理。

## 4. 接入范围

当前受控执行适配 DeepSeek/方舟官方直连的 `openai` LLM、`doubao_stream`/`doubao_recording` ASR、`huoshan_double_stream` TTS。其他付费适配器必须在接入同等准入和结算后才能开放；不支持的托管配置明确拒绝，不能借旧全局凭据执行。

纯本地 ASR `fun_local`、`vosk`、`sherpa_onnx_local` 保留本地推理，不消耗供应商调用额度；部署仍需对应模型和依赖。远程 `fun_server` 不属于此本地豁免。设备端语音处理也不因本轮升级被伪装成云供应商消费。

平台评测和官方后台任务需要显式的平台服务身份、模型/用途范围、独立凭据及额度。租户任务保留租户工作空间归属。没有配置就拒绝执行，不能由系统自动选一个用户付费。

DeepSeek 余额查询使用部署环境中的独立财务凭据和明确账号标识，不再从模型配置读取用户密钥。火山账单继续使用独立费用中心凭据。资源包仅查询、诊断和提醒，不购买、续费或切换。

历史共享供应商账号下的远端热词库枚举、导入入口已关闭，明确返回“供应商词库导入尚未接入独立凭据”，不会发起上游请求；工作空间热词编辑和批量粘贴词条保留。

## 5. 初始化与升级边界

新增表由 Liquibase 登记迁移。发布前备份数据库和密钥加密主密钥，核对工作空间的固定负责人和成员关系，保留业务资源与账目原 ID。不能通过重挂历史记录来伪造归属。

首次员工初始化只接受本机显式指定的 `XIAOZHI_SECURITY_OPS_BOOTSTRAP_FILE`。清单要求仅文件所有者可读，初始化状态持久消费，默认关闭；无公开初始化接口，删除员工不会重新打开初始化。启用网页 IAM 自助模式时，至少两名独立治理人员分别负责申请与批准，不能把原超级管理员自动映射为全权员工。

生产用一次性只读挂载向 manager-api 提供初始化文件，文件所有者须与容器内运行用户匹配，服务完成初始化后移除启动配置与挂载。当前生产 Compose 不自动提供此环境变量与挂载，首次初始化需由部署负责人显式配置。不要把清单、真实密码、TOTP 种子、恢复码或供应商密钥写进仓库、镜像和日志。具体字段以 `OpsBootstrap.Manifest` 和固定岗位目录为准。

未提供初始化文件时服务可以启动，但运营身份不会自动产生；员工申请和恢复申请在初始化状态消费前均拒绝，不写入员工或身份申请。该检查与初始化锁定同一状态行，避免匿名申请抢先阻塞初始化。首次启动应保持外部流量关闭，直到迁移、初始化和启动验证全部完成。

本次升级先停止旧应用访问，完成备份，再启动新 manager-api：Liquibase 先执行表结构迁移并使旧用户会话过期，随后启动任务分别消费员工初始化清单、加密归档旧模型秘密并清除相应配置缓存。两个启动任务没有固定先后顺序；任一失败都不能开放流量。当前容器健康检查只验证 TCP 端口，不能证明这些任务完成，须确认本次启动日志出现 `AdminApplication.main` 在 `SpringApplication.run` 返回后打印的文档地址行，并核对 `ops_bootstrap_state.consumed=1`、迁移记录和无异常重启。如果初始化已消费但另一启动任务失败，重启前先移除初始化配置，不能再次运行清单。旧版本仍依赖的全局秘密会被归档，不能让新旧应用同时使用同一数据库继续服务，也不能把镜像回退当作数据库回滚。

仅部署程序不会自动开通模型服务。启用前必须配置有限岗位、用户凭据库存、已批准模型、平台费率和发行额度，再通过本人空间与受邀协作场景验证；旧登录会话和含秘密配置的旧缓存需要按迁移策略失效。

### 小团队三账号模式

已完成首次初始化的环境可通过受控部署维护调整为以下三个运营账号；各岗位的范围仍以 `OpsPermissionCatalog` 为准，不授予 `IAM_REQUEST`、`IAM_APPROVE` 或身份委派权限。

| 账号 | 职责 | 固定岗位 |
| --- | --- | --- |
| `ops-keys` | 模型与额度 | `ALLOWANCE`、`CREDENTIALS`、`RATES`、`MODEL_CATALOG`、`SUPPORT` |
| `ops-resources` | 内容与系统运维 | `ALLOWANCE_POOL`、`OFFICIAL_CONTENT`、`OTA`、`OPERATIONS` |
| `ops-finance` | 财务与审批 | `SUPPLIER_FINANCE`、`ALLOWANCE_REVIEW`、`MODEL_REVIEW`、`CONTENT_REVIEW`、`OTA_REVIEW`、`AUDIT` |

额度发放池管理、额度发放和额度复核分别由三个账号承担；模型、官方内容和 OTA 的发布与审批仍由不同账号执行。所有现有业务审批、岗位冲突检查和禁止自批规则继续生效，不因减少账号而跳过。三个账号均不得读取用户聊天、音频、私人记忆或知识库正文。

匿名只读 `GET /ops/auth/identity-policy` 提供网页身份申请与恢复的可用状态，不返回员工名单或身份因素。缺少有效的 IAM 申请或审批岗位时，前端关闭 `enroll`、`recover` 入口，服务端在接受申请或消费恢复码之前拒绝请求；策略读取失败也不能按可用处理。该检查防止恢复码已消费却无人审批，不代替申请时和批准时的身份、委派与职责分离校验。

此模式下，员工新增、登录因素恢复和岗位调整由受控部署维护处理。维护前备份数据库与相关加密主密钥，核实目标员工、身份依据和批准的岗位范围；已有员工保留原 ID、业务归属及审计历史，维护操作留痕并撤销受影响会话，身份因素只向本人安全交付。维护不得读取租户隐私、放宽岗位冲突、重开已消费的 bootstrap 或新增公网密码重置旁路。当前没有可直接调用的通用恢复工具，不能把本段当作可跳过核验的重置命令。

### 网页 IAM 自助模式的初始化、激活与恢复

以下流程适用于配备独立 IAM 申请、审批人员的部署。当前首次初始化清单仍要求这两类岗位；三账号模式属于初始化完成后的受控调整，不能用无 IAM 清单绕过首次初始化校验。

1. 首次安装先提供 `XIAOZHI_CREDENTIAL_ENCRYPTION_KEY`，再通过一次性只读挂载提供初始化 JSON。根字段为 `employees`，每人包含 `username`、`password`、`totpSecret`、`grants` 和 `delegations`。后两项是 `{roleCode, scopeType, scopeId}` 数组：治理岗位分别使用 `IAM_REQUEST`、`IAM_APPROVE`，范围均为 `PLATFORM / identity`。委派数组限定该治理人员可以为其他员工申请或批准哪些岗位，不等于本人拥有这些业务权限；两名治理人员都需要目标岗位的精确委派范围。岗位与资源组合以 `OpsPermissionCatalog` 为准。
2. 初始化清单需要至少两名独立员工。密码至少 14 位，包含大小写字母及数字；TOTP 使用至少 32 字符的 Base32 种子。初始人员分别保管自己的因素；清单仅用于受控部署交付，初始化成功后移除环境配置和挂载并妥善处置清单。初始化不会自动分配任何租户身份。
3. 身份策略允许申请时，后续员工在 `ops.html#/enroll` 自行设置账号、密码和验证器，填写验证码后保存页面仅显示一次的新恢复码。申请 24 小时内由 `IAM_REQUEST` 员工确认身份，再由另一名 `IAM_APPROVE` 员工批准；申请人本人不能代替任何审批人。身份激活后尚无业务岗位，须另走“岗位与授权”的申请、独立审批流程。
4. 已登录员工可在运营首页生成本人恢复码，需要当前密码、图形验证码及未使用的 TOTP 动态码。刚登录后应等待验证器刷新。新恢复码替换旧码，仅回显一次，请保存到本人密码管理器，不交给运营审批人员。
5. 丢失登录因素且身份策略允许恢复时，员工在 `ops.html#/recover` 提交旧恢复码，并自行设置新密码与新验证器。恢复码在提交被接受时即消费，同时撤销已有会话；新因素与新恢复码在独立确认、批准后生效。恢复只更新身份因素，不恢复已撤销或过期的岗位。没有有效恢复码、申请已过期或 IAM 岗位缺失时，网页没有跳过验证、代设密码或重开初始化的入口，须转受控部署维护核实处理。

身份治理列表和审计只显示身份标识、操作和状态，不返回密码哈希、验证器种子或恢复码。官方模板和本地文本/问答知识库通过运营端另建草案、审批后发布；已发布内容不可原地修改，普通用户只能选用已批准版本。工作空间模板继续在空间内使用，旧“提交中心审核”入口已关闭且不再修改模板状态，已有记录保留。
