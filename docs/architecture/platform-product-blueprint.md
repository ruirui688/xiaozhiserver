# 平台产品化蓝图

本文是产品化目标架构与实施口径。已实现能力见[平台服务额度与运营隔离](platform-service-and-operations.md)，
供应商账单口径见[模型管理](../models/model-management.md#11-模型用量与实际消费管理)，
空间与负责人的既有约定见[工作空间与组织管理](workspace-organization-management.md)，
生产升级统一遵循[生产部署入口](../deployment/private-docker-release.md)。
历史审计与方案推演见[产品化规划报告](../reports/platform-productization-plan-2026-10-12.md)。

文档中的“已实现”“待实现”以代码事实为准；目标是方案，不是上线证明。

## 1. 一句话定位

平台自己承担模型采购：用户不配置供应商密钥，服务额度由平台运维统一下发，
在自己的工作空间或受邀协作的工作空间中使用官方直连模型。运营人员分岗位管理密钥、额度、官方资源
和固件，但**没有任何岗位可以读取用户对话、音频、记忆或私有知识库正文**。

## 2. 已确定的产品决策

以下为 2026-10-12 与产品负责人确认的决策，后续实现以此为边界：

| 编号 | 决策 | 影响 |
| --- | --- | --- |
| D1 | **一人一把供应商密钥**：沿用库存分配模型，`ai_platform_credential` 库存表 + 注册时按供应商分配 | 保留供应商侧按 Key 对账与单独吊销能力；受供应商 Key 配额硬约束，见 §4 |
| D2 | **额度由平台运维统一下发** | 用户只查看额度、用量与流水；注册试用政策能力保留且默认关闭，不承诺注册即获额度，见 §5 |
| D3 | **当前用户端不提供额度申请、充值、支付、提现或转账界面** | 额度发放由运维岗位与内部政策控制；一切“余额”都是平台服务额度，不是用户资金 |
| D4 | **调用使用所在工作空间固定负责人的密钥与额度** | 每用户保留独立凭据和个人额度；受邀协作不改扣成员账户，不提供负责人转让 |
| D5 | **运营岗位不可读取用户内容** | 岗位权限目录中不存在全租户内容权限；支持岗位不能代登录、不能重置密码取身份 |
| D6 | 平台额度账与供应商实际成本账分开 | 平台扣减额、预占额不得标成供应商实际成本；实际成本必须有官方金额证据 |
| D7 | 工作空间是资源归属与协作边界，不是独立钱包 | 不成立工作空间独立余额；工作空间限额只是负责人账户内的消费约束 |
| D8 | 只有工作空间：每用户默认拥有自己的空间，可直接邀请协作 | 默认标记不限制邀请，不要求额外新建团队或转换类型；投入转向额度、凭据、运营可见性 |

## 3. 授权模型

### 3.1 三类身份

| 身份 | 会话 audience | 数据边界 | 说明 |
| --- | --- | --- | --- |
| 产品用户 | `USER` | 自己获授权的空间、智能体、设备、额度 | Web 用户端 + 移动端 |
| 平台员工 | `OPS` | 按岗位权限与资源范围 | 独立账号、独立 TOTP、独立会话，员工主体没有租户 `userId` |
| 内部服务 | 服务密钥 + 服务预算账户 | 显式模型/用途范围 | 平台评测、官方内容构建等后台任务，不冒用客户账户 |

用户会话不能调用员工接口，员工会话不能调用租户内容接口。前端隐藏菜单不是权限依据：
Java 同时校验会话 audience、岗位权限和资源所有权。

### 3.2 岗位与权限（已实现）

岗位模板由代码限定（`OpsPermissionCatalog`），员工不能编辑权限字符串或委派上限。

| 岗位 | 权限 | 明确不具备 |
| --- | --- | --- |
| `ALLOWANCE` 额度运营 | `allowance.read/grant/freeze` | 供应商密钥明文、用户内容 |
| `ALLOWANCE_POOL` 发放池 | `pool.read/adjust` | 单用户额度发放（与 `ALLOWANCE` 互斥） |
| `ALLOWANCE_REVIEW` 额度复核 | `allowance.review` | 自行发放（与 `ALLOWANCE`、`ALLOWANCE_POOL` 互斥） |
| `SUPPLIER_FINANCE` 供应商财务 | `pool.read`、`supplier.bill.*` | 用户内容 |
| `CREDENTIALS` 凭据运营 | `credentials.read/write/revoke/assign/rotate` | 用户内容；不能随意改模型目标地址 |
| `RATES` 费率 | `rates.read/write` | 额度发放 |
| `MODEL_CATALOG` 模型目录 | `model.catalog.*` | 租户私有内容 |
| `MODEL_REVIEW` 模型复核 | `model.catalog.approve` | 自行发布（与 `MODEL_CATALOG` 互斥） |
| `OFFICIAL_CONTENT` 官方内容 | `official.resource.*`、`prompt.catalog.*` | 租户私有草稿与知识库 |
| `CONTENT_REVIEW` 内容复核 | `official.resource.approve` | 自行发布（与 `OFFICIAL_CONTENT` 互斥） |
| `OTA` 固件 | `ota.read/upload/publish` | 用户音频与对话 |
| `OTA_REVIEW` 固件复核 | `ota.approve` | 自行发布（与 `OTA` 互斥） |
| `OPERATIONS` 运维 | `system.read/write`、`device.diagnostics.read` | 用户正文；无任意线上调试 |
| `SUPPORT` 客服 | `users.read`、`users.status` | 密码/令牌、代登录、聊天与音频 |
| `IAM_REQUEST` / `IAM_APPROVE` | 身份治理 | 互斥；不能自批；不能创造通配权限 |
| `AUDIT` 审计 | `audit.read` | 凭据明文、内容正文、改账 |

**互斥约束由服务端强制执行**：申请/执行/复核岗位必须分离；身份治理岗位不能同时持有业务操作岗位。
权限目录中不提供 `tenant.chat.read:any` 一类全租户内容权限。

## 4. 凭据分配与密钥库存（D1 的硬约束）

### 4.1 已实现

- 凭据库存表按供应商管理未分配密钥，`ai_platform_credential_fingerprint` 以哈希阻止同一上游密钥重复入库。
- 注册时 `PlatformAccountService.ensureUser` 为 `DEEPSEEK` / `VOLCENGINE` 各分配一份库存密钥；
  库存不足时写入 `PENDING_CREDENTIAL` 状态，**不回退到他人密钥或全局共享密钥**。
- 密钥密文保存（`CredentialCipher`），浏览器、移动端、设备只能读掩码与状态。
- 轮换只改指针，历史归属保留（`ai_platform_credential_operation` 保证幂等）。
- 已分配密钥不回收给他人；吊销走 `status='REVOKED'`。

### 4.2 必须正视的供应侧天花板

一人一把 Key 的模型在规模上不是无限的，官方事实如下（核查于 2026-10-12，见规划报告 §7.1）：

| 约束 | 事实 | 后果 |
| --- | --- | --- |
| 火山方舟普通 API Key 配额 | 主账号默认 **50 个**，可申请扩容 | 用户数超过配额即无法开通 |
| 火山 IAM API Key | `CreateApiKey` 支持为指定 IAM 用户创建，超限返回 `LimitExceeded` | 可评估自动化，但需独立控制创建身份的权限与幂等补偿 |
| DeepSeek Key 创建 | 无公开的自动创建 API | 只能控制台人工创建后受控入库，运营负担随用户数线性增长 |
| DeepSeek 并发 | **按账号限速，与 API Key 数量无关** | 多发 Key **不能**扩容、也**不能**隔离并发；Key 提供的是访问撤销与部分用量标识 |
| 豆包语音 Key | `CreateAPIKey` 与 IAM 的 `CreateApiKey` 是不同接口 | 必须按实际启用的 ASR/TTS 协议分别验证 |

结论：**一人一把 Key 必须配套“库存水位治理”，否则产品会在用户增长时静默卡死。**
Key 数量不是成本隔离手段，成本与额度隔离由平台侧准入与账本负责。

### 4.3 库存治理要求（待实现）

| 要求 | 口径 | 状态 |
| --- | --- | --- |
| 库存水位可见 | 运营后台按供应商展示 `INVENTORY` / `ACTIVE` / `PENDING_CREDENTIAL` 待开通用户数 | 已实现（`PlatformCredentialInventoryService`） |
| 低水位告警 | 每个供应商可配置最低库存阈值（`xiaozhi.platform.credential-min-inventory`），低于阈值在凭据页给出告警 | 已实现 |
| 待开通队列可检索 | 列出 `PENDING_CREDENTIAL` 用户与注册时间，按等待时长排序，供运营按顺序补 Key | 已实现 |
| 补 Key 有闭环 | 运营入库后可对待开通用户一键执行现有幂等 `assign` | 已实现（凭据页"补齐凭据"） |
| 触发扩容 | 达到供应商配额的 80% 时，产品/运营按官方流程提交扩容申请；扩容周期需纳入容量规划 | 流程要求，人工执行 |

供应商配额与扩容方式必须在发行前核实到“预期用户规模下够用”，
未满足时应先限制注册发放节奏，而不是静默让用户停在待开通状态。

## 5. 额度生命周期（D2 落地口径）

### 5.1 状态流转

```text
注册 ──► 创建服务账户 ──► 运维按授权下发额度（`allowance.grant`）
           │
           ├─ 发放池不足 ──► 保持未发放，等待运维补池并重新处理（不阻断注册）
           │
           └─ 发放成功 ──► 可用额度 = granted - spent - reserved
                             │
   调用 ──► 预占 reserved ──► 结算 spent ──► 释放剩余预占
                             │
   额度用尽/冻结 ──► 新付费调用拒绝（仍在途调用按原快照结算）
                             │
   运维核实额度需求 ──► 按岗位权限下发 ──► 恢复可用
```

用户端只保留查询与使用，不展示额度申请、申请记录或支付相关入口。
运维统一下发包括授权人工发放和经运维启用的自动发放政策；用户额度流水仍如实展示已生效的
试用等政策来源及历史发放结果，不提供自行领取或启用政策的按钮。
已有 `ai_platform_allowance_request` 表、接口和后台处理能力只保留内部兼容与历史追溯，
不属于当前发布的用户体验。保留接口不代表启用用户申请，也不改变服务端身份与权限校验。
后续商业化可以保留架构设计，本阶段不增加支付实现、接口或界面。

### 5.2 保留的注册试用政策能力

以下为已实现、默认关闭的运维下发自动化能力，不是用户自助领额路径。
若以后由运维启用，仍须先确认政策、预算与防刷条件；不能仅凭代码存在承诺“注册即可用”。

| 要求 | 实现口径 | 状态 |
| --- | --- | --- |
| 幂等 | 同一用户 + 同一政策版本只发放一次；以账本 `entry_key` 唯一约束兜底 | 已实现 |
| 政策版本化 | 试用金额、生效时间、政策标识由配置项固定；改金额即改政策版本，不影响历史用户 | 已实现（`trial_policy` 列） |
| 受发放池约束 | 与人工发放共用 `ai_platform_pool`，池不足时**不发放、不报错、不阻断注册** | 已实现 |
| 受每日上限约束 | 复用运营每日发放上限，防止注册洪峰一次性抽干发放预算 | 已实现 |
| 可追溯 | 账本 `entry_type` 与原因字段记录政策版本，不记录密钥或用户内容 | 已实现（`SYSTEM:TRIAL` 记账主体） |
| 防刷 | 试用发放按用户去重；同一手机号/设备批量注册的治理属于风控范围，另行设计 | 按用户去重已实现；风控待设计 |

配置项：`XIAOZHI_PLATFORM_TRIAL_ENABLED` / `XIAOZHI_PLATFORM_TRIAL_AMOUNT` /
`XIAOZHI_PLATFORM_TRIAL_POLICY` / `XIAOZHI_PLATFORM_TRIAL_MAX_USERS`（默认关闭）。

**发放池必须先有余额**：全新部署时 `ai_platform_pool.total = 0`，
若不先执行 `pool.adjust`，所有新用户都会停在“未发放”。这是上线检查项，不是故障。

### 5.3 额度用尽后的用户路径

| 环节 | 要求 | 状态 |
| --- | --- | --- |
| 感知 | 用户端显示可用额度、预占中、累计已用；明确“额度由平台运维统一下发” | 当前发布口径 |
| 提示 | 按真实拒绝原因分别提示，**不得为了播报提示继续调用付费 TTS** | 已实现（本地提示音频 + 原因细分） |
| 下发 | 运维直接按岗位权限与发放池余额下发，无需用户提交申请；发放池管理、发放、复核职责保持分离 | 已实现 |
| 结果 | 用户在额度流水中查看发放结果，内部操作在审计事件中追溯 | 已实现 |

零额度用户仍保留登录、查询、导出本人获授权数据和额度查看能力。

### 5.4 拒绝原因与用户提示对照

准入拒绝返回业务错误码，屏幕文字按码给出对应提示（`core/handle/llmErrorHandle.py`）。
**未在白名单内的错误码一律回落到通用文字提示**，避免泄露服务端内部文案。

| 业务错误码 | 用户看到的文字 | 用户下一步 |
| --- | --- | --- |
| `ALLOWANCE_EXHAUSTED` | 服务额度已用完 | 联系平台运维处理 |
| `TEAM_ALLOWANCE_LIMIT` | 本工作空间已达使用上限 | 联系工作空间负责人 |
| `PAYER_FROZEN` | 账号服务已暂停 | 查看服务状态，等待平台处理 |
| `WORKSPACE_DISABLED` | 当前空间已停用 | 查看空间状态 |
| `PENDING_CREDENTIAL` / `CREDENTIAL_SERVICE_NOT_READY` | 模型服务待开通 | 等待运营补齐密钥 |
| `CREDENTIAL_CHANGED` | 模型凭据已更新 | 稍后重试 |
| `MODEL_NOT_ADMITTED` | 当前模型不可用 | 重新选择已批准模型 |
| 其他 / 未知 | 模型服务暂不可用 | 查看额度与服务状态 |

语音播放共用的本地提示音 `config/assets/tts_notify.mp3`，不会逐项播报上述具体原因，也不调用付费 TTS。文字与提示音均不包含密钥、地址或上游响应原文。

## 6. 调用准入与两套账

### 6.1 调用链（已实现）

```text
身份与资源校验 → 解析负责人 → 锁定可用额度 → 预占有界用量 → 持久保存调用标识
  → 确认开始 → 使用许可内凭据访问批准供应商 → 按可信用量幂等结算
```

- `admit` 按 attempt 幂等；`start` 防止重复派发；`extend` 必须先增加预占才能发送下一段付费数据；
  `settle` 保留原归属；`release` 仅释放确定尚未执行的调用。
- 许可有短期到期时间与硬截止时间；新调用与续占都重新检查授权、账户与凭据状态。
- 结果未知或用量不完整时保留待核对预占（`state='UNKNOWN'`），不虚构零消费。
- Python 侧 SQLite 补传队列保存调用与结算能力引用，不保存模型 API Key、提示词或音频，必须持久挂载与备份。

### 6.2 两套账

| 台账 | 主用途 | 是否对用户展示 |
| --- | --- | --- |
| 平台服务额度 | 发放、预占、结算、冻结 | 本人及获授权工作空间的额度与用量 |
| 供应商实际成本 | 官方应付/已付、抵扣、采购、对账 | 默认留在运营后台 |
| 供应商余额与资源包 | 现金/赠金、资源包余量与有效期 | 一般不展示；由平台保障可用性 |

## 7. 运营不可读取用户内容的实现边界

这是产品的对外承诺，必须同时满足：

1. **权限目录层面**：不存在全租户内容权限；付费负责人、工作空间管理员、普通使用者不等价于内容可读。
2. **接口层面**：聊天正文/标题/摘要、音频播放/下载/实时预览、记忆及来源、私有知识库原文/分块/检索调试、
   维护 trace 与附件，各自单独检查权限并使用短时、限动作的内容范围票据。
3. **客服层面**：取消返回新密码或可登录令牌的功能，禁止员工代用户登录或强制加入租户工作空间；
   找回密码由用户本人通过已验证渠道完成。
4. **运营统计层面**：只使用必要的脱敏标识、数量、时长、状态与金额；
   不得把对话标题、用户提示词或私有知识库名称写入财务报表与导出。
5. **旁路层面**：运行日志、APM、错误堆栈采样、调试工具、备份和对象存储不得成为旁路；
   内容加密、独立密钥管理和访问审计一起实施。
6. **变更运行行为岗位**：凭据管理员不能把模型目标地址改到自己的服务器；官方模板维护者不能发布未审查的
   数据外传工具；OTA 发布人员只能发布经审查、可追溯签名的构建产物。

**必须诚实说明的边界**：应用权限、内容加密和受控发布可以阻止日常运营访问，
但普通服务器架构**不能承诺**拥有宿主机 root、数据库明文访问或任意部署代码权限的人绝对拿不到运行时明文。
如需更强保证，需要独立 KMS、机密计算与远程证明，或改变端云处理方式，
详见[聊天数据安全参考](chat-data-security-reference.md)。这些基础设施权限不应作为普通运营岗位常驻权限发放。

## 8. 空间与协作（D7、D8）

| 概念 | 口径 |
| --- | --- |
| 工作空间 | 每用户默认拥有自己的空间，可以直接邀请其他用户协作；不划分个人或团队类型 |
| 负责人 | 工作空间调用统一使用负责人的密钥与额度；当前版本不提供转让 |
| 工作空间限额 | `total_limit` / `daily_limit` 是负责人账户内的消费约束，不产生新余额 |
| 绕道防护 | 负责人名下的调用共享同一额度账户，并发预占原子校验，不能靠多工作空间绕过上限 |

协作流程为“选择工作空间 → 邀请成员 → 设置角色与限额”，无需额外创建工作空间或转换空间类型，
新增投入优先给额度、凭据、运营可见性与发布治理。

## 9. 运营可见性指标（待实现部分见 §4.3、§5.3）

| 看板区域 | 指标 |
| --- | --- |
| 服务健康 | 准入拒绝率、待结算异常数、补传队列积压、许可超时 |
| 额度 | 发放池可用、已授予、未使用、已消耗；今日发放额与操作员限额占用 |
| 凭据 | 各供应商库存水位、待开通用户数、轮换与吊销待办 |
| 供应商 | 已确认成本、对账覆盖率、资源包临近过期、符合条件却持续现金付费的线索 |
| 治理 | 待审批的权限申请、额度发放复核、模型/内容/固件发布审批；历史额度申请仅供内部兼容处理 |

因为用户不充值，**不得**把发放额度当作营业收入，再据此计算虚假利润率。

## 10. 实施阶段与验收

| 阶段 | 可验收交付 | 关键门槛 |
| --- | --- | --- |
| P0 权限与数据边界（已实现） | 有限员工岗位、内容权限、取消旧全权旁路、密钥加密、空间与负责人模型 | 任意岗位组合都拿不到租户内容权限；旧会话失效，空身份拒绝 |
| P1 凭据与额度执行（已实现） | 用户独立凭据开通、负责人路由、个人账本、调用前预占、付费入口接入 | 无跨用户借 Key/扣费；并发、重试、轮换、故障结算正确 |
| P2 用户额度体验与运营可见性（进行中） | 运维统一下发、用户额度与用量查询、凭据库存告警、运营看板 | 用户端无申请或支付入口；池不足不阻断注册；待开通可检索可补齐；额度耗尽有友好提示 |
| P3 成本与智能运营 | 细粒度对账、资源包诊断、容量与补贴成本分析 | 每个实际金额有官方证据；无法关联的诚实留空；不自动购买或切换 |

P2 已落地的部分：运维按授权发放额度、用户额度流水、凭据库存水位与待开通队列、
额度耗尽按真实原因提示（额度不足 / 工作空间上限 / 账号暂停 / 待开通）。
Web 与移动端统一移除用户额度申请与支付相关展示；既有后台申请能力保留内部兼容。
注册试用政策能力保持默认关闭。P2 仍待完成的部分：运营首页的汇总待办、试用防刷风控。
**这些完成前，不应把“注册即可用”作为对外承诺。**

验收至少覆盖（在规划报告 §11 基础上补充）：

1. 重复注册、并发分配、Key 库存用尽、创建超时、轮换与吊销；绝不串用凭据。
2. 注册试用额度：同一用户重复触达只发放一次；改政策版本后历史用户不受影响；发放池不足时注册仍成功。
3. 额度耗尽：用户收到联系平台运维的友好提示，无申请或支付入口；运维按权限下发后调用恢复，用户可查询对应流水。
4. 凭据库存：低于阈值有告警；待开通队列可检索；补 Key 后一键补齐且不重复分配。
5. 所有工作人员直接请求用户内容接口、签发音频票据、导出私有知识库、重置密码取登录能力均被拒绝。
