# 服务端提醒任务中心

本文定义日程安排、周期执行、负载保护和设备下发的统一边界。系统总览见[项目架构](project-architecture.md)，设备传输见[设备交互链路](device-interaction-chain.md#48-日程提醒主动播报)，语音授权见[功能插件](function-plugin-architecture.md#设备日程提醒)。

## 1. 范围与事实边界

任务中心负责保存安排、计算下一次执行时间、持久化执行结果、控制下发负载和维护历史。生日、会议、闹钟等业务复用同一中心，不为每个业务或每条日程启动独立线程。它不是任意代码、任意 URL 或任意 MCP 工具的通用执行平台。

本轮不涉及设备固件。产品暂定“休眠设备可以被服务端唤醒”，作为下游投递能力假设；现有适配器仍通过已认证的在线 WebSocket/TTS 接纳请求，没有连接时返回离线，不伪造唤醒或播放成功。接入真实唤醒通道时应扩展下发适配器，不复制周期调度与业务存储。

`DELIVERED` 继续仅代表下游接受播报入队，不代表扬声器播放结束，更不代表用户听到。当前 Realtime 管线没有独立主动通知 TTS，不能声称已支持。生日的农历规则、健康周期预测、设备本地闹钟、用户确认回执均不是本轮已实现能力。

## 2. 数据与职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 语音插件 / 管理 API | 把明确请求转换为经校验的安排 | 每轮检查全部日程、到点调用 LLM 决策 |
| 安排定义 | 标题、目标、时区、重复规则、初始时间锚点、当前执行游标 | 提前展开无限次重复执行 |
| 执行记录 | 区分某一次执行、记录尝试及最终结果 | 把一次失败解释为整个周期永远失效 |
| 调度器 | 有界领取、恢复、全局下发预算、滚动下一次 | 持有全部历史日程的内存列表 |
| 下发适配器 | 校验目标、发送固定文本、分类接受/拒绝 | 修改日程规则或假造物理播放回执 |

MySQL 是持久事实源。原 `ai_device_reminder` 保留稳定 ID 与旧接口语义，承载安排及唯一下一次游标；执行历史独立保存。创建和推进不能依赖进程内定时器存活。进程重启后依据持久游标与有期限的领取权继续处理。

语音和小程序访问同一份安排。既有请求不传重复规则时，新建按一次性处理；旧客户端编辑周期安排时，缺省规则必须保留已有规则，不能悄悄变成一次性。显式取消整个安排后，不得再推进下一次。

## 3. 周期规则

`recurrence` 使用受限结构，而不是允许任意脚本或无限复杂表达式：

```json
{
  "frequency": "WEEKLY",
  "interval": 1,
  "weekdays": [1, 2, 3, 4, 5],
  "until": "2027-10-13T23:59:59+08:00"
}
```

- `frequency` 为 `ONCE / DAILY / WEEKLY / MONTHLY / YEARLY`。
- `interval` 为 1 至 365；`weekdays` 仅用于每周规则，使用 ISO 周一 1 至周日 7，首次日期必须匹配所选星期。一次性规则拒绝重复间隔和截止时间。
- `until` 可省略；提供时必须含时区偏移，不能把没有偏移的时间当作服务器本地时间。
- 计算依据初始本地日期、时间和 IANA 时区。每次推进不能把已经调整过的日期当成新的初始锚点。
- 每月 31 日跳过没有 31 日的月份；每年 2 月 29 日跳过非闰年。不能先落到月末再永久漂移。
- 夏令时跳过的本地时间按时区规则顺延；重复出现的本地时间只执行较早一次。

每个安排仅保留一个下一次待执行游标。长时间停机恢复后，处理当前过期执行并计算未来一次，不逐日补发全部漏掉的历史。这样工作量受当前到期安排数量和批次预算约束，而不与停机天数相乘。

## 4. 负载边界

负载控制要覆盖数据库、Java 执行器和 Python 接纳端，不能只在最外层加一个限速器：

1. 到期查询、过期恢复、历史维护均为带上限的批次；查询只读候选标识，按到期索引定位。
2. 有限工作线程与有限在途任务，领取数量受实际可用执行容量约束。没有容量时将任务留在数据库，不创建无限内存队列。
3. Java 下发预算使用数据库共享状态，多副本不能各自获得完整额度；数据库预算不可用时拒绝继续放量。
4. Python 在 TTS 入队之前执行独立进程级准入，控制短时突发、设备冷却与防重复存储容量。它不冒充跨 Python 副本的集群限额。
5. 离线、忙碌、暂时过载采用有上限的退避和抖动，并受最大尝试次数与执行有效期共同约束。相同执行重试使用同一请求标识。
6. 已完成执行历史按配置期限分批清理；活动安排、未终结执行和仍有效的防重复依据不得作为普通历史直接删除。

调度不调用 LLM。播报文案在保存时确定，只有被接纳的下发才进入现有 TTS 管线。普通对话的供应商调用额度不由本中心接管；提醒准入上限不能被描述为整个平台所有 TTS/LLM 请求的上限。

容量存在取舍：低预算保护实时对话，但集中到期可能延迟或超过有效期。不能同时承诺“任意任务量、固定低负载、全部准时”。调整预算前需要检查到期峰值、最老待执行延迟、下发耗时、拒绝率和数据库连接池余量。

### 默认预算与调节边界

Java 配置位于 `application.yml` 的 `xiaozhi.reminder`，各副本须保持一致；Python 配置位于本地 `server_notification_limits`，管理 API 模式也保留本地值，不接受设备配置覆盖。

| 项目 | 默认值 | 范围或含义 |
| --- | --- | --- |
| Java 扫描周期 / 候选批次 | 1 秒 / 20 条 | 最短 1 秒，每批最多 100 条 |
| Java 下发线程 | 每实例 2 个 | 最多 8 个，无等待队列 |
| Java 集群下发预算 | 每数据库秒窗 4 次 | 最多 20 次；跨秒边界可能出现双窗突发，不是滑动窗口 |
| 单次执行重试 | 最多 8 次、有效期 10 分钟 | 分别最多 20 次、30 分钟，两者先到为准 |
| Python 接纳 | 每秒补充 4 个额度，突发容量 8 | 每进程独立，不代表集群总额度 |
| Python 待播 / 设备冷却 | 最多 32 个 / 2 秒 | 冷却结束且管线空闲才释放待播占用 |
| Python 防重复回执 | 32768 条 / 1 小时 | 有效回执不能因容量满而被驱逐；保留期限不短于 1 小时 |
| 执行历史清理 | 超过 30 天，每 10 秒最多 200 条 | 共享数据库门控，单维护线程，过期处理批次结束也检查清理机会 |

正常到期与过期处理分道，过期记录不消耗网络下发额度。工作空间轮转只在当前有限候选页内生效，不保证所有租户的严格全局公平。清理是有预算的渐进维护，并非到第 30 天立即删除；持续过期洪峰、低清理配置和数据库延迟都可能拉长实际保留时间。默认清理理论预算高于默认正常下发预算，但仍应观察历史增长。

安排定义、终态一次性安排及原创建请求幂等依据继续保留，不自动删除用户历史。因此本实现约束的是扫描方式、执行并发、重试与内存占用，不承诺全部磁盘存储永远固定。新增 `GET /reminders/{id}/executions?limit=20` 按工作空间鉴权查询单次执行历史，最多返回 100 条。

Java 每分钟输出固定字段统计：领取、限流、接纳、重试、未送达、过期、下发累计及最大耗时、所选候选页最老延迟。它不是全库最老积压指标；Python 提供有界接纳计数快照，不新增按设备生成的指标序列。

## 5. 安全、并发与投递一致性

用户 API 验证当前工作空间权限与设备归属；运行时接口在共享服务密钥之外验证设备和智能体绑定。投递前再次核对当前绑定，不能信任历史创建时的身份快照。

领取权有期限并带唯一令牌。旧执行者失去领取权后不得覆盖新执行结果。执行标识须区分安排版本和本次计划时间；普通重试不换标识，编辑或下一周期不能被误认为旧执行的重复。

创建请求防重复指纹与当前调度游标分离：周期滚动不能导致同一语音请求重试被错误判为不同请求。缺少返回结果时，客户端应查询确认，不把不确定结果当成创建失败后任意重建。

语音相对时长由 Python 转为绝对时间后提交同一 Java 接口，不新增调度器。每个连接最多保留 256 个创建请求锚点（参数与身份摘要、原始绝对时间）；同 ID 重试复用原时间，变更内容或目标身份被拒绝，满额拒绝新建而不驱逐旧锚点。操作只有短临界区，没有新增线程、定时器或后台扫描，连接销毁后释放。重放由 Java 先查持久幂等记录；未存在的安排仍须通过当前时间窗口。该缓存不是跨连接持久去重，新连接或新调用 ID 仍可能形成新安排。

首次具体日期解析拒绝夏令时跳时或重叠的无偏移输入；这是创建时的歧义确认，不改变上文已经保存的周期规则在后续执行中的顺延/选择策略。时间输入合同见[功能插件](function-plugin-architecture.md#设备日程提醒)。

设备换绑、编辑取消与下发的原有串行化保护不得仅为缩短代码而删除。当前下发需保留有界 HTTP 超时与有限并发；若未来去除网络调用期间的数据库行锁，必须同时引入下游可验证的版本栅栏或同等保证，再修改取消语义。

Python 的接纳去重仍有进程重启及路由边界。多 Python 实例需将设备连接路由到所属实例；不得把单进程缓存说成跨进程严格恰好一次。网络返回丢失、部分 TTS 入队失败与实际播放失败需要区别描述。

日志和统计不得包含提醒正文、密钥或任意用户提供的指标标签。指标维度保持固定，不按每个用户、设备、安排 ID 创建时间序列。

## 6. 兼容、发布与验收

数据库变更只能新增 Liquibase 迁移，原已发布 changeSet 不变。旧数据默认一次性；升级时保留已有提醒、状态、请求标识与归属。结构兼容不等于调度行为兼容，不能让不认识周期规则的旧调度器与新调度器同时处理新周期安排。

旧小程序继续使用既有增删改查接口。新增周期字段由服务端和语音工具提供；本轮不因此声称小程序已经具备周期编辑界面。

验证分层：

- 单元测试覆盖时间边界、游标推进、配置上限、重试预算及权限兼容。
- 合成并发测试覆盖相同请求只接纳一次、超预算拒绝、冷却恢复及容量耗尽。
- 独立 MySQL 测试覆盖迁移、真实索引、数据库共享预算、领取竞争和持久恢复；只使用隔离测试库，不连接生产库。
- 上述测试不等于生产容量压测，不调用真实外部模型，也不证明设备物理播放或休眠唤醒。

生产发布仍走[唯一部署入口](../deployment/private-docker-release.md)，发布前备份数据库并协调调度器版本切换。当前源码、测试、镜像和生产状态分别记录，不以本地测试通过代替已部署。

## 7. 设计依据

- [Alexa Reminders API](https://developer.amazon.com/en-US/docs/alexa/smapi/alexa-reminders-api-reference.html)：重复规则、时区、播报内容使用统一提醒协议。
- [Home Assistant Timer](https://www.home-assistant.io/integrations/timer/)：计时状态恢复与错过触发是不同语义，不能认为重启恢复自动补发所有事件。
- [EventBridge Scheduler quotas](https://docs.aws.amazon.com/scheduler/latest/UserGuide/scheduler-quotas.html)：保存数量与触发速率分别治理。
- [EventBridge RetryPolicy](https://docs.aws.amazon.com/scheduler/latest/APIReference/API_RetryPolicy.html)：退避重试同时受次数和有效期约束。

这些是公开能力参考，不声称已经知道商业助手的内部数据库或采用相同部署架构。本项目继续复用现有 MySQL 和服务模块，不引入新消息系统作为默认前提。
