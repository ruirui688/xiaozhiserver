# 部署资产治理策略

本文定义部署资产的长期归档边界。当前阶段只固化规则，不移动既有 Dockerfile、Docker Compose 文件或脚本。

## 目录职责

`docs/deployment/` 负责部署流程说明，包括安装教程、升级步骤、发布说明、排障经验和操作背景。文档应解释为什么这样部署、什么时候使用哪种方式，以及失败后如何处理。

`deploy/` 负责可执行部署资产，包括 Docker 编排模板、服务器安装入口、升级入口、发布入口、环境变量模板和发布校验清单。部署人员、CI 或脚本应能直接消费这些资产。

`scripts/` 负责本地开发、检查和当前兼容命令。部署相关脚本在迁移到 `deploy/` 前，原路径必须继续可用，避免破坏已有文档、CI 和用户习惯。

## deploy 分域

- `deploy/docker/`：Docker 构建和容器运行资产。
- `deploy/server/`：本地服务器安装、升级、回滚和运行时目录初始化资产。
- `deploy/release/`：镜像发布、版本打标、私有仓库推送和发布验证资产。

新增资产应先判断属于哪个部署域，再放入对应目录。无法明确归类时，应先补充 README 中的边界说明，再新增文件。

## 当前兼容保留清单

以下文件暂时保留在原位置：

- `scripts/docker-build-private.sh`
- `scripts/install-private-docker.sh`
- `main/xiaozhi-server/docker-compose_all.yml`

这些文件已经被现有部署流程引用。后续迁移必须满足：

1. 原路径保留兼容入口。
2. 新路径在 `deploy/` 对应域中有清晰归属。
3. `docs/deployment/` 中的教程同步改为稳定入口。
4. 迁移说明包含替代命令、兼容期限和回滚方式。

## 判断规则

如果内容是教程、解释、步骤说明或排障记录，放在 `docs/deployment/`。

如果内容会被 `docker compose`、安装脚本、发布脚本、CI 或部署人员直接执行或复制使用，放在 `deploy/`。

如果内容主要用于开发者本地启动、格式检查、测试辅助或一次性维护，放在 `scripts/`。

## 迁移原则

- 先建立兼容入口，再迁移真实实现。
- 先更新文档引用，再宣布旧入口废弃。
- 不在同一次变更中混合大规模文件搬迁和行为重构。
- 生产数据目录、配置文件路径和镜像标签策略变更必须单独说明风险。
