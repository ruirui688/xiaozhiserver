# 当前仓库与官方上游能力审计

本文回答三个问题：当前仓库相对官方源码增加、改变或放弃了什么；这些差异为什么存在、是否仍有必要；后续同步官方更新时应采用什么策略。本文是时间点报告，不替代各专题架构文档和[本地定制记录](../local-customizations.md)。

## 1. 结论

当前仓库不是官方项目的简单增强版，而是面向私有生产环境、长期运营和微信小程序管理场景的产品分支。官方上游仍是通用协议、provider 和基础管理能力的主要来源；本地分支则把语义控制、长期记忆、本地知识库、模型评测、工作空间、安全和私有部署做成了跨模块闭环。

差异不能用“本地更强”概括：

- 本地必须保护的部分，是已经形成数据模型或运行契约的能力，例如长期记忆、本地知识库、工具门控、工作空间、模型评测和 ACR 发布流程。
- 官方应选择性吸收的部分，是协议兼容、provider 修复、并发修复、移动端质量修复和 RAGFlow 稳定性改进。
- 本地明确缩小了数字人测试端、多语言移动端等范围；其中部分是产品取舍，部分可能需要重新评估。
- 2026-07-22 工作区中的记忆、知识库和移动端修复尚未提交，不能描述为已发布能力。

## 4. 为什么必须保留这些差异

### 4.1 产品目标不同

官方仓库服务广泛的开源硬件和快速部署场景，优先覆盖协议、provider 和基础控制台。本地仓库服务的是持续运营的端云平台，需要组织隔离、微信入口、配置审计、模型选型、长期记忆维护和私有发布，这些能力天然跨越 Python、Java、Web、Mobile 和数据库。

### 4.2 数据与依赖边界不同

官方知识库依赖 RAGFlow，本地增加本地切片和检索，是为了私有数据、离线或受限网络环境以及可控成本。官方 provider 级记忆可以完成对话摘要，本地长期记忆还必须支持人工纠错、遗忘、重建和审计。两者不是同名实现的简单替换关系。

### 4.3 确定性和安全要求不同

语义控制、工具门控、资源所有权和生产认证解决的是“模型或设备不能越过服务端决策”的问题。即使官方新增相似功能，也必须逐条比较契约，不能用目录覆盖方式同步。

### 4.4 历史分叉造成双向缺口

455 个本地独有提交并不意味着官方修复可以忽略。165 个官方独有提交中已经包含设备自动更新、类型安全、上下文注入、异步化、并发死锁、服务端 AEC、智能体配置快照、FunASR 语言配置、移动端质量和 RAGFlow 稳定性等候选改进。本地也删除或缩减了官方数字人、移动端设备配网和多语言界面。后续应建立同步分支逐域审查，而不是把任何一侧当作完整超集。

## 7. 待集成修复的发布边界

截至本次审计，以下内容只存在于未提交工作区：

这些修复已有单元测试、Java 全量测试、Web/Mobile 构建等自动验证记录，但仍未执行真实微信授权、RAGFlow、外部 LLM、Redis/数据库升级和设备端端到端验证。正式发布前必须把工作区按领域审查、提交并在目标环境联调，不能仅依据本文判定已上线。

## 8. 复核方法与限制

本次使用 Git 对象和源码做只读比较，主要命令包括：

```bash
git fetch upstream --prune
git rev-parse HEAD upstream/main
git merge-base HEAD upstream/main
git rev-list --left-right --count upstream/main...HEAD
git diff --name-status upstream/main...HEAD -- <领域路径>
git show upstream/main:<代表性文件>
rg --files docs -g '*.md'
scripts/docs-facts --check
scripts/docs-check
```

未启动长期服务，未调用真实外部模型、微信、RAGFlow 或生产基础设施。本报告对“能力存在”的判断来自代表性源码、目录、测试和文档，不等同于生产环境验收。
